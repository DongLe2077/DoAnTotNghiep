# Authentication, shared screens and owner CT1–CT8 browser checks

`ui-polish.spec.ts` adds six real-backend browser cases for native dialog focus/close/reopen in ordinary and reduced-motion modes, dashboard skeleton/error/manual retry, owner unsaved-change cancellation/discard, clean navigation after saving, logout from a dirty form and tenant draft retention at 390px. It uses only the normal isolated E2E database. The separate `npm run presentation` mode uses `.cache/presentation/owner-demo.sqlite`, its own cookie/storage and ports 5175/18002; it persists manual edits and never resets the E2E or old manual-demo databases. [Presentation and checkpoint instructions](../../docs/presentation-guide.md), [acceptance record](../../docs/presentation-polish-acceptance.md).

Latest full Chrome run on 30 October 2026 after presentation/UI work: **94/94 passed in one 27.0-minute run**, one worker and zero retries. Frontend unit checks passed 131/131 and the production build passed. The presentation-only review passed 30 readonly checks/10 screenshots, followed by 15 rehearsal checks with writes to its own synthetic data; restoring the checkpoint matched all records, invoice balances and private photos.

On 30 October 2026, the related billing/UI/new-feature run passed 14/14 Chrome cases across `owner-billing.spec.ts`, `ui-acceptance.spec.ts`, `zz-bulk-meters.spec.ts` and `zz-property-pdf.spec.ts`. The new suites cover property revision conflicts, bank account leading zeros, real private PDFs for both roles, revoked grants, failed/retried downloads and logout cancellation; multi-room decimal readings, invoice locks, stale-row recovery, committed-response-loss replay and mobile/tenant restrictions. Bulk fixtures create active tenant accounts before representative check-in, preserving the real business validation. Recovery assertions match requests by idempotency key, without assuming queue ordering. See [the acceptance record](../../docs/property-pdf-bulk-acceptance.md).

Run `npm run test:e2e` from `D:\KLTN\frontend` after installing dependencies and a Playwright Chromium browser. To use an installed Chrome browser instead, set `PLAYWRIGHT_CHANNEL=chrome`. PHP must be available on PATH (or set `PHP_BINARY` to its executable) and the backend Composer dependencies must already exist.

The suite starts a real Laravel PHP server on `127.0.0.1:18000` and Vite on `127.0.0.1:15173`. Both ports must be free. Optional `E2E_API_PORT` and `E2E_FRONTEND_PORT` variables change them.

The test backend uses only `frontend/.cache/e2e/auth.sqlite`, separate session/cache/log directories, a fresh encryption key and fixture-only accounts. It never changes the normal backend `.env` or connects to `rental_management`. Fixture preparation creates the base schema and applies extension migrations only to the disposable SQLite database; it refuses database/storage paths outside that directory. `APP_ENV=e2e` deliberately keeps real cookie and CSRF protection enabled.

Covered flows: owner and tenant login; persistent sessions after reload; role restrictions in both router and API; invalid/disabled/unknown-role accounts; logout and rejection of the old session cookie; CSRF rejection; current-password validation; password-change logout and new-password login; login rate limiting; mobile overflow and menu/account navigation; cross-tab logout; failed logout retaining its live session and displaying an error.

The additional `design.spec.ts` suite checks the public `/design` page with API and external asset requests blocked. It verifies local Vietnamese fonts, linked field errors, modal keyboard focus and Escape, room filters/details/demo forms, tenant whole-room pricing, and layouts at 360/390/768/1280px. Design screenshots are stored in `.cache/design/screenshots/`. All preview data is synthetic and no preview action is persisted.

The `notifications.spec.ts` suite uses real Laravel session/CSRF HTTP endpoints with a small isolated relational fixture: users, tenants, rooms, occupancy/stay/representative records, an explicitly granted outstanding invoice, maintenance requests and notifications. Its `invoice_balances` and `active_invoice_access` SQLite views follow the backend test schema so that current visibility checks run normally. Base fixture tables are created directly and extension migrations apply only to this disposable SQLite file. The six original authentication accounts retain empty inboxes. Separate `e2e_notify_owner`, `e2e_notify_tenant` and `e2e_notify_empty` accounts exercise the new shared screens.

Notification checks cover private owner/tenant lists, current-permission filtering, pagination, type/unread filters, persistent mark-one/read-all and account scoping, fresh authorized invoice/maintenance detail requests, genuine empty inboxes, mobile layouts, retry after network failure, clearing old private cards, session-expiry/account-switch cleanup and no automatic replay after a CSRF failure. They also verify the shared inbox destination survives login and forbidden/missing-page screens offer a safe return. Happy paths use the actual backend. Failure cases deliberately intercept requests to simulate network loss, CSRF rejection or a subject becoming unavailable. A separate pagination edge case models list/count responses shrinking from 16 unread items to 15 while keeping authentication, CSRF, notification IDs and the mark-read request on real Laravel; the URL must normalize to page 1.

`ui-acceptance.spec.ts` checks the owner and tenant screens at 320px, a low-height owner sidebar, mobile tenant navigation, explicit role guidance on forbidden pages, a failed account-switch logout retaining the session and a successful retry followed by login as the other role. Review screenshots use the `acceptance-` prefix. Announcement tests also cover clearing and reselecting a room without duplicated selected labels.

Screenshots, traces and the HTML report are written under `.cache/e2e`. The named authentication and notification review images are in `.cache/e2e/screenshots`. These are synthetic, disposable fixture accounts and never use a real application password or data from `rental_management`.

`owner-management.spec.ts` covers CT1–CT3 using actual API writes against the same isolated SQLite backend: room CRUD, common rent review and preservation of agreed rent; service precision/edit/disable/delete; optional tenant accounts; one/multiple residents, capacity limits, representative replacement, service price intervals/end, transfer/checkout/history; and an explicitly retried CSRF failure. A fixture-only `room_occupancy_summary` view supports catalog queries. Screenshots use the `ct1-`, `ct2-`, and `ct3-` prefixes. No owner-management test writes to the application's MySQL database.

`owner-billing.spec.ts` covers real meter CRUD and invoice locks, preview/issue and stale preview rejection, historical representatives, invoice access/revocation/reminder deduplication, partial/full payment and receipts. A committed payment with its response deliberately dropped is retried with the identical payload/key after a real session expiry and login, without adding a second receipt. Invoice deep-link filters are checked as well.

`owner-cash.spec.ts` covers create/review, edit/delete/audit/revert, unknown creation recovery after reload, cross-tab pending request preservation, CSRF/manual retry, version conflicts and a successful restore whose response is lost. Ledger filters, grouping, pagination, empty/error/mobile layouts and tenant restrictions use real backend data. `owner-maintenance.spec.ts` covers filters, private photos, processing/completion notifications, stale versions and readonly completed requests. `owner-reporting.spec.ts` compares dashboard/receivable values with API responses, separates current occupancy/all-month debt from selected-month figures, checks invoice/room/group debt views and links, failed refresh cleanup and role restrictions.

## Manual owner demo

`tenant-portal.spec.ts` covers tenant NT1–NT4 through real Laravel writes and reads: personal room/profile/history and service price snapshots, ordinary members versus representatives, empty/unlinked profiles, partial/full invoice receipts and revoked grants, real multipart images and image-only retry after a committed response is lost, malformed/oversized image validation, real completion/checkout and notification links, manual CSRF retry, session cleanup and role/author restrictions. A deterministic PNG faucet illustration is generated in memory as synthetic test data. No real photos or account records are read for fixtures.

`npm run demo` starts the isolated Laravel fixture with a separate `owner-demo.sqlite` file and `rental_owner_demo_session` cookie, Vite on 5174 and PHP on 18001. Both ports must be free. Only the exact demo filename is allowed when `E2E_DEMO=1`; normal tests continue to require `auth.sqlite`. Both modes enforce disposable path/storage/run guards and never modify MySQL. Tests create the base fixture and apply the extension migrations to that isolated SQLite file. Demo restarts preserve existing data and uploaded files; explicit schema upgrades run only after validating and backing up the exact demo database. The demo supervisor asks its backend child to stop PHP over IPC when shutting down on Windows.

The manual owner is `chutro_demo` / `Demo@2077`; B202 has an active stay, services and last month's meter readings ready for invoice preview. Other sample rows include debt, cash transactions and maintenance requests/photos. See [the Vietnamese self-test guide](../../docs/owner-self-test.md). This fixture contains synthetic passwords/data only. Generated SQLite files, logs, photo fixtures, screenshots and reports remain under ignored `.cache/`.

Additional user-requested manual accounts: `admin` / `123` (owner) and `user` / `123` (tenant, TEST-USER). Existing account passwords are preserved on restart; the initial setup's explicit reset flag is not enabled by default.

`announcements.spec.ts` adds four workflows: selected-room delivery to ordinary members, stale-preview rejection after an account change, a committed send with its response lost followed by reload/manual reconciliation, tenant inbox/full-content reading and owner read counts; all-room delivery and exclusion of later residents; empty audiences/search and mobile layout; and explicit retry after CSRF rejection. Content is rendered as text, including a synthetic script string that must not execute. Tests use separate browser contexts for the two roles and inspect real Laravel records. Screenshots use the `announcements-` prefix.

`repair-history.spec.ts` covers genuine submission/progress/note-edit/note-clear/completion events, lost processing response and explicit version-conflict reconciliation without duplicate history, historical notes, author access after checkout, pagination, foreign-tenant denial, truthful legacy baselines and refresh-error cleanup. It runs after the fixed-count notification/owner fixtures because submitting its own reports legitimately creates owner notifications. It does not alter the pre-seeded report records. Review images use the `maintenance-history-` prefix.

Vite excludes `.cache/` from file watching and direct HTTP file serving, so generated reports cannot reload an open manual demo and private fixture files cannot bypass the API through static URLs. Latest full Chrome run on 23 October 2026 after both portals were completed: 62/62 passed in 9.4 minutes; frontend unit checks 110/110 passed. The tenant flow also exercises the actual file chooser button, image-only replay, real malformed/over-dimension PNG rejection, and a readonly invoice after revoked access.
